<!--CLEAR-->
A handoff of record, written for whoever picks this up cold, and it says exactly where it sits in the reading order.

It begins by defining its subject in one frame, insisting this is a single growing thing rather than several separate ones. Then it states the ambition: a place where this can be studied publicly, following nature, asking honestly whether this is the right maths, never overclaiming and never smuggling in a reward.

Then a numbered list of non-negotiables, each with a citation so it can be checked rather than taken on faith. Several are worth reading even out of context. Never claim anything from a process merely existing; quote the named machine gate or say not verified. Only one node of that kind, ever. One supervised writer per store. A default that must stay byte-identical, guarded by a named test and a stored fixture. A human-typed confirmation on anything outward, with the rule that authority is never widened and only evidence is. And a lesson from an earlier mistake, that viability must emerge rather than being handed over as food or as reward.

One of those entries is unusually honest housekeeping. It records that another machine had rebooted shortly before this document was written, that several units are disabled, and that anything reading its state will see exactly that. The page calls this honest rather than a bug.

The reading order is tiered, from the always-loaded contract, through the chain of decision records, the code that carries the truth, the science lane, and the engine with its guards. One tier is labelled as trustworthy only through its banners, and one file is named as not authoritative at all, with its replacement given.

The inventory of what landed is mostly infrastructure for honesty rather than features. There is a gate ledger — a list of results that can be added to but never edited — with a rendered view and a schema for its rows. There is a shared file of fenced words loaded from both languages — words a claim may not use — so the rule cannot drift between them. And there is a runner scaffold, and hooks with a mirrored version for the automated pipeline, so the ship gate and the ban on percentage scoring are enforced in both places.

The workstreams are then summarised with what has landed and what is held as a specification queued for review. That is the part a reader should notice: several of the most interesting pieces are designs waiting on a verdict rather than working code, and the page says so plainly instead of blurring the two together.

The closing ask is written as an instruction to the next agent. Read these three documents in order, check the ledger for the current state, and treat the section listing what is not landed as the queue. Then the rules for acting. Run the review before touching the sensitive files, and land the verdict before the change. Version any schema you touch, use the standard header on any receipt, the file recording a run, and never claim from a process existing. It ends with a rhythm rather than a plan. Take one thing, do it honestly, emit the receipt, update the ledger, and hand off to the next agent.
